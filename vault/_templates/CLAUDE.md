# vault/_templates/CLAUDE.md — Vault Conventions Starter

**This is the tracked starter.** On first vault setup, it is copied to `vault/CLAUDE.md` (gitignored, per-user). Edit your copy to add personal preferences; this file stays as the universal default — change it only when the convention itself is changing for everyone.

Operating manual for any AI agent working **inside the vault** (creating notes, doing reading prep, surfacing cross-refs). This file is self-contained — you can work with just the vault and not the surrounding project repo. If the project repo is also present, root `CLAUDE.md` covers project-level orientation (repo layout, tooling, commit/push norms) and `docs/planning/DECISIONS.md` covers architectural decisions and rationale.

---

## What this vault is

- Plain markdown on disk. Any database is a rebuildable cache.
- Source of truth for the user's own Bible study notes, accumulating over months/years.
- Currently used in Obsidian. Format must remain tool-agnostic — never use a feature that locks data into a specific tool.

## Layout

```
vault/
├── CLAUDE.md                   — per-user operating manual (gitignored; copy of this starter)
├── _templates/                 — note + scaffolding templates (do not link to; do not backlink to)
├── bible/                      — Bible text (generated by tools/import-usfm.ts; do not hand-edit)
│   └── {Book}/{NN}.md          — e.g., Gen/01.md … Rev/22.md
│   └── {Book}/{NN}_strongs.json — sidecar Strong's data (per DECISIONS D11.1)
├── docs/                       — vault-side reference data (generated; do not hand-edit; per D23)
│   └── reading_plans/{plan}.md — e.g., m_cheyne.md (generated by tools/import-mcheyne.ts)
└── notes/                      — the user's notes (the actual external brain)
    ├── bible/                   — book-overview pages; one per book + a master Bible.md (seeded by tools/import-usfm.ts, idempotent — never overwrites user edits)
    ├── people/
    ├── places/
    ├── concepts/
    ├── events/
    └── readings/
```

## Translation

Currently **BSB** (Berean Standard Bible). When a second translation is added, `bible/` will be reorganized to `bible/{translation}/{Book}/{NN}.md`. Until then, paths under `bible/` carry no translation segment, but each chapter file declares `translation: BSB` in frontmatter.

## Verse references in notes

Always use full Obsidian block-ref wiki-links:

```markdown
[[bible/Gen/01#^v1|Genesis 1:1]]
[[bible/Rom/08#^v28|Romans 8:28]]
[[bible/Psa/119#^v105|Psalm 119:105]]
```

- Display text after `|` uses the spelled-out book name + `Ch:Vs` (or `Ch:Vs–Vs` for ranges) — `Genesis 1:1`, not `Gen 1:1`. Psalms cite as `Psalm 119:105` (singular), matching the chapter-file H1.
- Path uses 3-letter abbreviation + 2-digit zero-padded chapter.
- Block ref `^vN` targets the verse anchor inside the chapter file.

**Verse ranges:** link only the start verse; show the range in display text.
```markdown
[[bible/Eph/05#^v22|Ephesians 5:22–33]]
```

**Cross-chapter ranges (rare):** link the start; mention the end in prose.
```markdown
The household codes ([[bible/Eph/05#^v22|Ephesians 5:22]] through Ephesians 6:9) form one literary unit.
```

**Never use:**
- `[[Genesis 1:1]]` shorthand — does not resolve in stock Obsidian.
- `[Genesis 1:1](bible://...)` — no URI handler exists.
- `:` in any file path or anchor (invalid on Windows; portability landmine).

## Note-to-note links

Standard Obsidian wiki-links resolve by note title (the filename without `.md`):
```markdown
[[Abraham]]                — links to notes/people/Abraham.md
[[Covenant]]               — links to notes/concepts/Covenant.md
[[Abraham|the patriarch]]  — display "the patriarch", target Abraham.md
```

When display text matches the filename, the alias is unnecessary — `[[Moses]]`, not `[[Moses|Moses]]`.

### Filename rules (per D18)

Title case with spaces, ASCII (apostrophes permitted):

- Capitalize the first letter of nouns, verbs, adjectives, pronouns, adverbs.
- Lowercase articles (`a`, `an`, `the`), coordinating conjunctions (`and`, `but`, `or`, `nor`, `for`, `so`, `yet`), and short prepositions (`of`, `in`, `on`, `at`, `by`, `to`, `up`, `as`) — except as the first word of the title.
- **No apostrophes in filenames** (per D20 — Obsidian's rename interface won't accept them). Drop the apostrophe in the filename; preserve the apostrophe form as an alias in frontmatter so autocomplete and link resolution still find the note. Example: file `Centurions Servant.md` with `aliases: ["Centurion's Servant"]`.
- Examples: `Melchizedek.md`, `Mount Sinai.md`, `Tower of Babel.md`, `Kingdom of God.md`, `Anointing of Jesus by the Sinful Woman.md`.
- Ambiguous names disambiguate in the filename, then alias in display:
  - `Mary Mother of Jesus.md`, `Mary Magdalene.md`
  - `[[Mary Mother of Jesus|Mary]]`
- Numerals: spell out unless natural English keeps them (`First Temple`, not `1st Temple`); for Bible books keep numeric prefix in path codes (`1Sa`, `2Co`).

### Disambiguating book-name overlaps (per D27)

Some entity notes share a name with a book-overview note seeded by the importer (per D26). For example, both `notes/people/Job.md` (the patriarch) and `notes/bible/Job.md` (the book overview) exist. The shorthand `[[Job]]` is ambiguous — Obsidian resolves it to whichever file its index finds first, and that's not stable.

When the entity name might collide with a book name, link via the full vault-relative path:

```markdown
[[notes/people/Job|Job]]      — the person
[[notes/bible/Job|Job]]       — the book overview
[[notes/people/Jonah|Jonah]]  — the prophet (vs `notes/bible/Jonah.md`)
```

Verse-anchor links (`[[bible/Job/26#^v6|Job 26:6]]`) are unaffected — they already carry the full path. The ambiguity only exists for the unanchored short form.

Common collision names (any of these may be a book *and* an entity): Job, Ruth, Esther, Daniel, Jonah, Joshua, Hosea, Joel, Amos, Obadiah, Habakkuk, Haggai, Zechariah, Malachi, Matthew, Mark, Luke, John, James, Jude, Titus, Philemon. When in doubt for any name that *might* be a book, use the full path.

**Alias-side collisions.** Some entity stubs carry a book-name as an alias — `notes/people/John the Apostle.md` aliases `"John"`, `notes/people/James Son of Zebedee.md` aliases `"James"`. The filename doesn't collide, but typing `[[John]]` could autocomplete to either the alias or the book overview. Obsidian disambiguates with a picker for the human, but agents writing links must still be explicit. **Don't write the bare alias** — link the full filename (`[[John the Apostle]]`) or use a piped display form (`[[John the Apostle|John]]`). Same rule, same reason: the link source must be unambiguous regardless of which alias resolution wins.

## Frontmatter schemas

All notes carry YAML frontmatter. Keep fields minimal; every field is a maintenance burden.

### Common fields (all note types)
- `type` — one of `person | place | concept | event | reading`
- `created` — ISO date `YYYY-MM-DD`
- `updated` — ISO date
- `aliases` — list of alternate names (Obsidian uses these for link resolution). Follow the same title-case rule as filenames (per D18): `["Christ", "Jesus Christ", "the Lord", "Son of Man"]`, not `["christ", "jesus christ", ...]`.
- `tags` — list of strings, lowercase-hyphenated

### `person` extras
- `era` — one of: `pre-flood`, `patriarchs`, `egypt-exodus`, `wilderness`, `judges`, `united-monarchy`, `divided-kingdom`, `exile`, `post-exile`, `intertestamental`, `gospels`, `early-church`, `unknown`

### `place` extras
- `region` — free-form (`canaan`, `mesopotamia`, `egypt`, `asia-minor`, …)
- `modern_location` — optional, free-form

### `event` extras
- `when` — rough dating, free-form (`c. 1446 BC`, `AD 30`, `unknown`)
- `where` — wiki-link to a place note
- `participants` — list of wiki-links to person notes

### `reading` extras
- `passages` — list of human-readable passage descriptions (`["Exodus 4:1-31", "Luke 7:1-50"]`). Always a list, even for single-passage days (per D16).
- `passage_links` — list of verse-anchor wiki-links covering the passages
- `status` — `prep` (before reading) | `read` (read but no reflection yet) | `reflected` (post-reading notes added)

The reading date itself is carried by the **filename**, not frontmatter — see "Reading-prep note filenames" below.

### Reading-prep note filenames

Daily reading-prep notes live at `notes/readings/YYYY-MM-DD (Day).md` (e.g. `2026-04-26 (Sunday).md`). The date prefix is what the Obsidian Calendar plugin keys on; the day-of-week parenthetical is optional but useful when scanning outside Calendar. Per D16, the filename is canonical for the reading date — no `date` field in frontmatter.

The H1 of the file carries the plan signature when relevant — e.g. `# M'Cheyne - Day 52` for a plan-driven reading, or just `# Reading` for ad-hoc. Plan name and plan day are not stored in frontmatter (would burden users not on a named plan).

### Reading-prep section split (AI-fill vs. user-fill)

Per D21 (supersedes D17), sections in a daily reading-prep note divide cleanly between AI and user:

**AI fills (mechanical):**
- `### Entities` (per passage) — links to people / places / concepts / events stubs.
- `## Connections back to prior notes` (shared tail) — grep results from the user's own prior notes that link into the day's passages.

**User fills (during/after reading; AI leaves a blank header):**
- `### Notes` (per passage) — single freeform scratchpad per passage. Absorbs cross-references, themes, questions, and during/after-reading observations into one stream the user dictates while listening or writes after reading.

AI agents working on reading prep must not pre-populate the per-passage `### Notes`. Even factual content (BSB editorial parallels, footnoted refs) shapes the reading. The chapter file under `bible/` already has those inline, navigable from the verse-link in the section heading.

The `status` frontmatter field tracks the lifecycle: `prep` = AI scaffold (entities + connections-back filled); `read` = user has read; `reflected` = user has filled the per-passage `### Notes`.

## Note body — H1 convention (per D19)

**Entity stubs (people / places / concepts / events) do not carry an `# H1`.** The blockquote lede is the first body content, directly under frontmatter. The filename is the title; Obsidian renders it at the top of reading view, and other markdown tools surface it via the file path.

**H1 is required where it carries information beyond the filename:**
- **Bible chapter files** (`# Genesis 1`) — generated by the importer for cat-readability outside Obsidian.
- **Daily reading notes** (`# M'Cheyne - Day 52`, etc.) — H1 holds the plan/day signature, which is not in the filename.

Rule of thumb: keep H1 when it says something the filename doesn't. Drop H1 when it would just echo the filename.

## Stub creation policy — eager

When you encounter an entity that doesn't have a note yet (during reading prep, or while extending an existing note):

1. Determine the type (`person | place | concept | event`).
2. Generate a slug per the rules above.
3. If `notes/{type}/{slug}.md` exists, do not overwrite — just link.
4. Otherwise, copy the template from `_templates/{type}-template.md`, fill in known frontmatter (era for people, region for places, etc.), and seed `## Key passages` with a verse-link to the passage that spawned this stub. Per D22:
   - **Skip the body lede** when title + aliases identify the entity unambiguously (`Moses.md`, `Mount Sinai.md`, `Binding of Isaac.md`).
   - **Add a one-sentence blockquote lede** above `## Key passages` only when scope is genuinely unclear from the title and aliases (`Antioch.md` — Pisidian vs Syrian; `Election.md` — theological term with multiple senses).
5. Don't write multi-paragraph commentary into stub bodies — leave them for the user to develop.

Stale stubs (empty body + zero inbound links + older than threshold) will be cleaned up later by `tools/lint-stubs.ts`. Do not preemptively avoid stub creation to dodge this.

## What you may do without asking (inside the vault)

- Create stub notes in `notes/{type}/` from templates.
- Create reading-prep notes in `notes/readings/` from `_templates/reading-template.md`.
- Append links/sections to existing notes (without rewriting their body).
- Extend a stub's body with concise summaries when prepping a passage that includes that entity.

## What requires the user's confirmation

- Modifying an existing note's body content beyond appending links/sections.
- Deleting any note (always).
- Renaming any note (breaks inbound links).
- Modifying anything under `bible/` (this is generated text — change the importer, not the output).

## Markdown style

- **Italic** uses `*word*`, never `_word_`.
- **Bold** uses `**word**`.
- **Avoid HTML in markdown** unless markdown has no equivalent — HTML breaks plain-text search and `cat`-readability.
- **No emojis** in any vault file unless the user explicitly asks.

## Vault-content hard rules

- **Quote, don't paraphrase.** When summarizing a passage, quote the text and link the verse — don't paraphrase Scripture in prose.
- **Mark interpretation as interpretation.** "Likely refers to…", "Possibly indicates…", "Traditional reading is…". Don't present commentary as if it were the text.
- **Don't invent.** If you don't recognize an entity or aren't sure of a fact, ask the user — don't fabricate a stub or claim.
- **Don't write commentary into stub bodies.** Stubs are seeds; the user develops them.
- **Don't annotate verse-link bullets.** In `## Key passages` (and similar lists), the bullet is just the link — `- [[bible/Job/22|Job 22]]`, not `- [[bible/Job/22|Job 22]] — Eliphaz's third speech`. Pick the right verse range so the link itself is informative, then stop. Any summary is the user's to add as they read; pre-filling it preempts that. *Caveat:* if a bullet already carries a summary on an existing note, leave it — that's user-written. The rule is about what AI writes, not about scrubbing what's there.
